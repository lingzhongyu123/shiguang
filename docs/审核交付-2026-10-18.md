# 拾光个人使用审核与修复交付

## 结论

产品方向符合个人口述日志需求。优先做好原文找回、记忆证据和恢复验证；现阶段不需要多用户、分布式队列或更复杂的摘要系统。保留八条相关记忆检索和深度复盘。

本目录是包含原项目未提交修改的审核副本。最终隔离回归已通过；已同步原项目并逐文件校验哈希，尚未推送 GitHub 或部署。

## 本次修复

| 优先级 | 问题及影响 | 副本中的处理 |
|---|---|---|
| P0 | 超时重试、重复投递、旧任务返回可能造成重复保存或覆盖状态 | 客户端稳定请求编号；服务端幂等提交；任务尝试版本；条目和任务完成同事务提交 |
| P0 | 刷新恢复可能覆盖新草稿或丢失失败原文 | 原文、模式、日期一起保存；服务端未完成列表；恢复与重试入口；不无条件清除失败原文 |
| P0 | 备份缺少失败任务原文，恢复后证据指向旧编号 | 新备份包含未完成任务和候选记忆状态；导入映射日志编号；恢复任务需手动重试（最终数据库回归已通过） |
| P1 | 编辑档案重建全表，导致证据链丢失 | 保留匹配记录和来源，移除条目停用；确认记忆只自动合并相同文本，避免相反含义误并 |
| P1 | 截断或破损 JSON 被当成有效记忆 | 截断输出判失败；损坏结构降级时不生成记忆或事件，展示处理提示 |
| P1 | 润色改动否定、推测性格、历史关联难核查 | 提示词加强事实边界；历史带来源编号；前端支持来源跳转；候选记忆可编辑确认 |
| P1 | 修改正文后旧分析仍像是最新结论 | 标记分析待重新核对，停用不一致的检索内容；保留原始口述 |
| P1 | 日期按提交时间混淆，周月总结范围不清 | 上海日期、用户选日期、事件日期；滚动 7/30 天明确起止，全量取数；过大输入明确失败 |
| P2 | 首条日志等待卡片不显示、刷新打断编辑 | 修复空列表骨架、轮询竞争与编辑保护；修正移动端提示文字 |

“只润色”强制不生成记忆和复盘，也不发送档案作为上下文。日常保留完整检索；模型调用总预算为普通 180 秒、深度 600 秒，这不是整个请求严格四分钟的保证，数据库和检索耗时仍需线上观察。

## 产品取舍

暂缓“正文先行”：先观察 flash 的真实等待体验，避免为了几十秒增加两阶段生成维护成本。目标闲置提醒暂缓，缺记录不能解释为没进展。历史关联可点回原文值得保留；旧的截断记忆与过度结论应由本人确认后修订，本次未擅自改动。
